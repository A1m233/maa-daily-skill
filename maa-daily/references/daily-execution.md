# 单账号日常固定执行器

- 最近核验日期：2026-09-15
- 官方来源：[maa-cli 运行器](https://github.com/MaaAssistantArknights/maa-cli/blob/main/crates/maa-cli/src/run/mod.rs)、[任务参数](https://docs.maa.plus/en-us/protocol/integration.html)。
- 边界：国服服务器游戏日；固定阶段和停止条件先做离线测试，真实覆盖范围以末尾验收记录为准。

本页拥有日常阶段顺序与本机调用配置。`daily_run.py` 是窄范围执行器，不是原生 MAA task，也不是定时器、账号管理器或断点恢复系统。首次接入先按[创建指南](create-task.md)确认业务偏好，再用[模板](../assets/daily-run.example.toml)引用已有 task。

## 分工与调用

- 原生前段 task：公招、商店、基建、按服务器游戏日装配的剿灭。
- 原生选关 task：只通过 maa-cli verbose dry-run 解析当日标准关卡；不重新实现星期规则。
- `drain_sanity.py`：普通清体力、用药和余量循环。
- 原生 Award task：用户选择的日常/周常、邮件、活动领取。
- `reward_check.py scan`：自行导航到任务页，再扫描；不依赖 Award 的结束页面。
- 执行器：固定顺序、阶段证据、停止条件和完整性汇总；不以任何一项 Completed 代替全部目标。

配置保存在本机 MAA config/policies/ 下，不放进原生 tasks/，路径相对于该配置文件解析。它只引用正式入口与用药策略，不复制每个账号的业务、星期表或密码。配置不构成未来无人值守授权。

```text
python <skill-root>/scripts/daily_run.py preflight --config <本机配置.toml> --maa <exe> --profile <profile> --account <本地别名> --output-dir <本地目录>
python <skill-root>/scripts/daily_run.py run --config <本机配置.toml> --maa <exe> --profile <profile> --account <本地别名> --output-dir <本地目录>
```

外层仍须确认模拟器窗口、设备/profile、无并发游戏操作者与可信账号。多账号先执行官方 startup 并检查本轮身份，再逐账号调用本执行器；`--account` 只是报告别名，不能充当身份断言。执行器不检查其它工具启动的 MAA 进程，调用者必须排除并发，包括会写 MaaCore 日志的 dry-run。

`preflight` 读取与 dry-run，不连接游戏、不部署资源；会建立本地证据/配置快照，不能称为零文件写入。先用 `daily_checks.py prepare` 部署资源，冲突按原流程处理，不自动覆盖。`run` 自己再次预检，不接受旧 preflight 作为运行许可。

## 固定顺序与停止点

前段 → 优先任务核验 → 普通清体力 → 最终 Award → 基建/奖励检查。

前段解析成独立进程依次执行，任一执行失败不继续同文件后续 task。存在剿灭时在它结束后立即核验优先目标，不能因为任务链结束就跳到普通清体力：

- `priority_goal = "weekly_cap"`：本轮须有达到每周上限的结算进度证据。
- `priority_goal = "configured_runs"`：本轮须核验已配置次数。券/普通代理资格与预算仍由调用者和创建流程确认。
- 当天没有装配剿灭：明确记录 `not_scheduled`，照常进入普通清体力。
- 优先目标未确认：停止；不自行降低目标或吞掉缺口。

剿灭完成不等于清体力完成。普通清体力必须调用组件取得新鲜读数；零场也要由组件证明不足一场。阶段或场次预算到达时报告 incomplete，不改为正常耗尽。

每个阶段前后检查国服服务器游戏日（UTC+8、04:00）；跨日后不自动继续下一阶段，也不把已有消耗归零。长战斗在当前进程内自然结束，不在换日瞬间强杀。

本轮报告保存在唯一目录：plan.json、原 task 源快照、dry-run 原文、processes.json、各组件报告与 daily-result.json。日常配置、选出的参数和用药策略在运行前固定；真实 task 在隔离配置中生成，不改原业务文件。

## 汇报与恢复

`daily-result.json` 固定列出 pre / priority / drain / award / checks。没有执行的阶段保持 pending；失败阶段保留原因，不允许省略缺项后汇报完成。

- completed：固定阶段完成且没有组件提醒；不是商店/基建全部游戏状态的额外断言。
- completed_with_reminder：阶段执行完成，但有基建未知、药物库存未知或奖励区间不足等提醒。
- incomplete：执行、必需前置或核验失败，剩余步骤列入 missing_steps。

基建仍是动作级证据，通常会保留提醒；奖励扫描返回有效区间但关键档位未知时同样提醒，不能改为已领取。扫描执行失败则本轮 incomplete，不能自动重试或切下一个账号。

没有 resume、skip 或自动导入旧报告选项。中断后由 Agent 按原报告核对已发生的业务，明确补跑范围，再调用已有独立组件；不得从头再执行以“恢复”已购买、已招募、已领奖的步骤。协作锁存在时不启动第二轮；异常遗留锁必须先确认旧进程结束再由操作者处理，执行器不抢锁。

## 首版范围

支持 TOML/JSON 原生 task 文件，要求 task 标签唯一，顶层仅 tasks；同名不同格式拒绝。解析 maa-cli 的 `Adding task [...] with params: {...}` 输出是窄适配：不认识的格式拒绝，不猜类型或忽略任务。Stage 必须唯一、times=0、药石预算零；普通日常暂要求成本表已收录，表外目标仍走通用清体力组件的显式成本接口。

前段不允许 StartUp、Award 或普通 Fight，防止重复切号、提前领奖或残留旧批量；剿灭必须明确选图且不使用恢复资源。最终文件只允许一个 award=true 的 Award，其它领取分支保留用户配置。模板不自动迁移用户文件。

已满周上限但本轮未产出结算进度时，当前优先门禁可能无法证明 weekly_cap；不要仅按零场当作已满。该状态需独立证据或后续扩展，不自动以历史报告绕过。
