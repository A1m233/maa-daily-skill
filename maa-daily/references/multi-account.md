# 单设备多账号的一次性运行

## 核验信息

- 最近核验日期：2026-08-18
- 实测基线：maa-cli 0.7.5，MaaCore 6.16.8；已验证账号 B 登录过期时失败关闭，也已完成登录态有效时完整 A→B 官方切号与共享业务 task 顺序执行
- 官方来源：[MAA 开始唤醒与账号切换](https://docs.maa.plus/zh-cn/manual/introduction/startup.html)、[maa-cli 使用](https://docs.maa.plus/zh-cn/manual/cli/usage.html)、[maa-cli 运行器源码](https://github.com/MaaAssistantArknights/maa-cli/blob/main/crates/maa-cli/src/run/mod.rs)
- 边界：只覆盖一个已确认设备/profile 上、多个已登录账号依次复用同一业务 task 的一次性请求；不覆盖多设备、并发、定时、长期无人值守或持久授权。

## 支持的目标

用户可以在一次请求中指定固定顺序的多个账号，让 Agent 对每个账号运行同一套日常。这里的“一次”指一次用户授权和一次工作流，不代表一个 `maa run` 进程。

每个账号必须：

- 已经登录在当前客户端的账号列表中，不输入密码、验证码或新的登录凭据；
- 能用当前 `maa startup --account-name` 支持的唯一登录名或片段区分；
- 使用已确认的同一个设备/profile；
- 明确继承同一套业务 task 和资源上限，或单独说明差异。

`account_name` 不要求是完整手机号或纯数字。当前真实客户端已验证可以使用登录列表中带 `****` 的脱敏显示字符串，只要该字符串或其片段在已登录账号中唯一即可。应原样复用可信列表/日志中的显示值，不要尝试从掩码重建完整手机号，也不要自行去掉 `*` 后猜测账号。

账号登录名、手机号或邮箱片段属于本地敏感配置。只在必要的本地 task、终端输入和日志核验中使用；对用户汇报时优先使用“账号 A / B”等别名，不写入公开仓库、Skill、eval 或公开报告。

## 官方切号入口与进程隔离

MAA 官方说明：账号切换会在每次执行“开始唤醒”时发生，只支持已经登录的账号，并要求 `account_name` 在已登录账号中唯一。maa-cli 把它暴露为预定义命令：

```text
maa startup Official --account-name <唯一登录名> --profile <profile> --batch
```

官方 CLI 文档使用 shell 的 `&&` 串联 `startup`、业务任务和 `closedown`，因此一次性多账号工作流也采用相同的 fail-closed 语义：只有前一条命令成功退出，才启动下一条。Agent 可以逐进程执行并检查退出码，不要求实际拼成一条 shell 命令。

maa-cli 会先把 task 文件中的所有任务依次 `append_task` 到同一个 Assistant，再调用一次 `start()`；MaaCore 的 `TaskChainError` 由 maa-cli 在整轮结束后汇总为进程错误。当前证据不足以保证“账号 B 的 `StartUp` 失败”后，属于 B 的资源变更任务一定不会继续在原账号上执行。

因此不要生成这种单进程队列：

```text
StartUp(A) → 日常(A) → StartUp(B) → 日常(B)
```

仅仅按账号拆成两个自定义 task 仍不够；如果一个进程内部仍是 `StartUp(B) → 日常(B)`，切号失败后业务任务仍可能落在原账号。改为同一次工作流中的两级隔离运行：

```text
maa startup --account-name A → maa run daily-main
→ maa startup --account-name B → maa run daily-main
```

只有未来版本提供并经当前环境验证的可靠失败隔离或账号身份断言后，才重新评估单进程串号；不要仅凭 dry-run 或 happy path smoke 放宽。

## 共享业务 task

共享业务 task 不包含账号目标，也不再包含会重复执行的无账号 `StartUp`。如果已有单账号日常以 `StartUp` 开头，保留原文件并派生一个仅移除该开头任务的业务副本，避免破坏原有单账号用法。业务副本示意：

```toml
[[tasks]]
type = "Award"
params = { award = true }
```

不要为每个账号维护一份完整日常，也不要为切号创建自定义 helper。账号目标只出现在当次 `maa startup --account-name` 命令中；先用本机 `maa startup --help` 核对选项，再运行共享业务 task。

账号名来自用户已知的登录记录或既有可信日志。不要打开模拟器界面进行视觉识别或点击来发现、选择账号，也不要传入虚构的“不可能匹配”名称探测账号列表；未匹配的 StartUp 可能长时间等待或重试。

用户明确要求“从现有日志里看”或等价表达时，先完成下面的本地只读发现，再决定是否缺少信息：

1. 用当前版本的 `maa dir log` 取得日志目录，不猜固定用户目录。
2. 在该目录的近期文本日志中检索 `account_name`、`CurrentAccount`、`AccountSwitch` 等账号证据。使用结构化命令参数时，把正则表达式作为一个参数传递，例如 `["rg", "-n", "-g", "*.log", "account_name|CurrentAccount|AccountSwitch", "<log-dir>"]`；不要把 `|` 误写成 shell 管道，也不要为了搜索启动第二份 MAA 或 MuMu。
3. 结合时间、相邻任务和登录结果区分真实已登录账号、测试探针、失败尝试与过期记录。日志中出现多个不同值，不等于它们都是本批次目标；优先使用与最近成功切号/运行链相关、能唯一匹配的脱敏显示值。
4. 账号证据与模拟器实例证据分开核验。账号可以来自 MAA 日志；MuMu 实例和启动参数应来自当前进程、管理器、多开器、快捷方式或端口对应关系。不要因为日志里找到了账号就猜实例编号，也不要因为实例已运行就声称可见窗口已打开。
5. 对用户只汇报“账号 A / B”等别名与证据状态，不回显完整账号值。只有完成上述检查后仍无法唯一辨认账号、顺序或实例时，才停止并询问最小缺失信息。

日志发现只能复用本机已经存在的登录标识，不构成读取密码、验证码或恢复完整手机号的授权。

## 执行门禁

执行前简短列出：设备/profile、账号别名与顺序、共享业务 task、每账号的资源影响上限，以及预计的 maa-cli 进程数。默认每个账号一次 `maa startup` 加一次 `maa run`；两个账号通常是四个进程。用户明确要求“把 A、B 都跑一次”且这些目标和影响已知时，已经构成本批次授权；不要在每个账号前重复确认。

按顺序执行：

1. 为当前账号取得已知且唯一的 `account_name`，不把模糊片段当成“最接近的账号”。
2. 运行官方 `maa startup <client> --account-name <name>`，等待进程结束或进入已有的运行时失联处理。
3. 从该命令的退出码、summary 和本次 MaaCore/maa-cli 日志共同核实切号；`AccountSwitch` 只证明尝试选择了目标记录，`StartUp Completed` 只证明启动链到达可结束状态，都不是目标账号身份断言。日志出现“登录已过期”、重新登录/认证提示、回退到“最近”账号或其他身份反证时，即使退出码为零也按切号失败处理。不使用 Agent 视觉或 GUI 点击补充判断。
4. 只有退出状态和日志都支持切号可信时，才启动新的 `maa run` 执行共享业务 task；等待结束并核实业务结果与设备状态。若登录已过期，由用户在游戏中手动恢复已登录状态，Agent 不输入密码、验证码或其他凭据。
5. 只有当前账号的两个进程都结束且状态可安全进入下一轮时，才开始下一个账号。
6. 任一账号切换失败、匹配不唯一、身份不确定、业务任务失败或状态无法恢复时，停止剩余账号并报告；不得为了“跑完整批”继续，也不得自动重跑已完成账号。

普通业务任务部分失败时同样默认暂停后续账号。只有 CLI 日志证明当前账号身份仍明确、没有资源风险且能通过已验证恢复路径回到安全起点，才可在本次既有授权内继续；报告中保留前序失败。

## 结果汇报

逐账号使用别名分类：成功、部分完成、正常跳过、切号失败、任务失败、未开始或结果未知。总结果只能从逐账号证据汇总，例如“账号 A 成功；账号 B 切换失败；账号 C 未开始”，不能用最后一个进程的退出码代表整批。

当前基线的真实 smoke 已证明两条关键路径。失败路径中，账号 B 的已保存登录态过期时，MaaCore 先记录选中 B，随后回到最近账号，而 maa-cli 仍把 `StartUp` 汇总为 `Completed`；这证明业务 task 必须拆进下一进程，并在 startup 后检查认证与回退日志。成功路径中，官方 `maa startup Official --account-name <B 的唯一脱敏显示名>` 明确退出账号 A、选择账号 B、完成登录和主页识别，随后新的 `maa run` 完成了 B 的共享业务 task；A 与 B 的业务进程均无 `TaskChainError`/`SubTaskError`。

该环境仍没有 CLI 级“当前账号就是目标账号”的强身份断言，因此成功 smoke 不取消日志门禁：应同时要求正向的退出、选中目标、登录/主页识别证据，并确认没有登录过期、重新认证或回退反证。把能力描述为“完整 A→B 顺序执行已验证，但身份核验仍是日志证据而非强断言”，不要外推到其他客户端或账号状态。
