## 按实际影响授权

不要为每条命令机械弹确认，也不要把一次“帮我看看”扩大成真实操作。

通常可直接进行的只读动作：

- 查看帮助、版本和 `maa dir`；
- 读取用户明确放在范围内的 profile/task；
- 查看已安装组件、进程和候选路径；
- 解释配置和官方资料。

需要当前请求明确覆盖或补充确认的动作：

- 下载/安装/更新 CLI、MaaCore、资源、VC++ Runtime 或 ADB；
- 启动模拟器、启动 ADB server、连接设备；
- 新建或修改用户配置；
- 运行会操作真实游戏的 task；
- 对多个已登录账号依次运行同一 task；
- 停止进程、删除候选/备份、回滚或替换文件。

用户已经明确说“运行我的日常”且目标 task/profile/设备和影响已知时，这就是本次执行授权，不再重复问一次。若执行前发现配置会实质变化、设备不唯一或资源风险超出用户描述，停止并补足上下文。

## 资源安全

- 源石默认禁止。任何非零源石策略必须来自用户明确、知情的当前意图。
- 理智药、临期药、加急许可、信用商店购买和自动确认招募会改变资源；根据用户偏好配置，不以示例替代选择。
- 参数名或单位不确定时读取当前官方协议。不要靠“看起来像”猜测 `stone`、`medicine`、次数、时间或枚举。
- 模板仅提供低风险起点，不代表完整日常或推荐配置。

执行前用简短摘要说明：

- task/profile/设备；
- 将进行的主要任务；
- 可能消耗的资源及其上限；
- 是否会启动或关闭游戏；
- 本次是否改过配置、是否通过 dry-run。

多账号请求还要说明固定账号顺序和独立 `maa run` 次数。账号匹配、运行与失败隔离的详细责任由 [单设备多账号的一次性运行](multi-account.md) 负责；本页不重复定义流程。

## 执行上下文与 MaaCore 边界

宿主可能提供多个命令执行上下文，它们对用户配置、资源目录、网络、进程、ADB 和桌面会话的可达性并不相同。真实 `maa startup` / `maa run` 应运行在已经证明能访问本次目标 profile、MaaCore 资源、必要更新网络、目标 ADB 端点和必要桌面会话的上下文中。一个上下文里的 `adb devices` 或其他只读检查成功，不能证明另一个上下文中的 maa-cli 与 MaaCore 具备同样条件。

真实命令持续无输出时，结合当前进程状态、命令自身输出、资源更新状态和本次 MaaCore 日志的时间边界判断是否已经进入 MaaCore：

- 本次出现新的 `TaskChainStart`、连接或其他 MaaCore 事件时，继续按具体任务、连接和长命令规则处理；
- 本次没有任何新的 MaaCore 日志时，先分类为“尚未进入 MaaCore 的执行前停滞”，不要写成账号切换、游戏界面识别或业务任务失败，也不要根据另一个执行上下文中的 ADB 成功猜测原因；
- 切换执行上下文前，先确认原进程已经退出、被明确取消，或仍由原运行时可靠持有并继续观察。只有原进程不会与新进程重叠，且另一个上下文已经证明满足本次运行条件时，才在既有授权内做一次有界重试；
- 同一前置停滞在兼容上下文中复现，或原进程终态无法确认时停止，报告可观测性缺口，不连续更换上下文或启动重复任务。

这些判断描述运行时能力，不绑定某个 Agent、权限模式或沙箱实现。宿主如何授权、取消和报告进程状态，仍以当前公开工具的实际结果为准。

## 真实进程的薄 runner

当前宿主能运行 Python 时，用 Skill 自带的 `scripts/run_with_evidence.py` 单独包裹每个真实 `maa startup` / `maa run` 进程。runner 不获得额外授权，也不改变 task、profile、设备或账号目标；它只在同一个执行上下文中运行原命令并收集证据边界。

```text
python <skill-root>/scripts/run_with_evidence.py \
  --report-file <本地临时目录>/<账号别名>-<阶段>.json \
  -- maa startup Official --account-name <唯一登录名> --profile <profile> --batch

python <skill-root>/scripts/run_with_evidence.py \
  --report-file <本地临时目录>/<账号别名>-business.json \
  -- maa run <task> --profile <profile> --batch
```

runner 使用待执行命令的同一个 `maa` 可执行文件调用 `maa dir log --batch`，在运行前后记录 `asst.log` 的文件大小和行号，再输出以 `MAA_EVIDENCE_JSON=` 开头的单行 JSON。只有当前环境已经证明 MaaCore 日志位于另一个精确路径时，才使用 `--core-log <path>` 覆盖自动发现；不要把示例或旧会话路径写死。

报告只保留可复核的非业务结论：

- 子进程与 wrapper 的退出码；
- 本次新增日志的起止行、日志是否缺失、未变化或发生轮换；
- 本次新增日志字节区间的 SHA-256，供后续检查组件拒绝已被替换的证据区间；
- `TaskChainStart`、`TaskChainCompleted`、`TaskChainError`、`SubTaskError` 的次数和行号；
- MaaCore `ERR` / `CRT` 行号，以及 `SubTaskExtraInfo.what` 的类型计数；原始 `subtask_error_lines` 完整保留，另列有上下文证据的 `conditional_subtask_errors` 与仍阻断的 `blocking_subtask_error_lines`。

runner 不保存完整命令参数或完整日志副本，`business_result` 固定为 `not_evaluated`。这意味着 runner 的零退出码仍不证明账号、购买、领取、招募、基建或资源消耗等后置条件成立；Agent 必须按报告给出的本轮日志范围继续核对相关业务证据。

退出行为保持 fail-closed：子进程非零时保留其退出码；子进程为零但没有取得可界定的新 MaaCore 日志时返回 `74`；子进程为零但本轮存在 `TaskChainError`、未消歧的 `SubTaskError` 或回调解析错误时返回 `75`。任一非零结果都停止同一多账号批次的后续进程；若宿主只把非零码统一显示为普通失败，精确值以报告中的 `wrapper_exit_code` 为准。报告只写本地临时或调试目录，文件名使用账号别名，不写入 Skill 仓库，也不包含账号标识。

#### 条件检查未命中与业务失败

MaaCore 的部分 `ProcessTask` 被上层当作布尔条件使用，未命中可产生 `SubTaskError`，但不等于资源动作失败。已核对 v6.16.8 的 [CreditShoppingTask](https://github.com/MaaAssistantArknights/MaaAssistantArknights/blob/v6.16.8/src/MaaCore/Task/Miscellaneous/CreditShoppingTask.cpp) 在购买后探测 `CreditShop-NoMoney`，命中才停止；[InfrastReceptionTask](https://github.com/MaaAssistantArknights/MaaAssistantArknights/blob/v6.16.8/src/MaaCore/Task/Infrast/InfrastReceptionTask.cpp) 对 `UnlockClues`、`EndOfClueExchange` 的返回值也允许条件未成立后继续。

脚本只对这三种调用形态做上下文分类，不让 Agent 按名称自行忽略错误：必须有同一进程/线程日志通道、任务类型与 taskid 下完整的任务链，精确的单节点 `ProcessTask` 失败，以及包围它的对应 `CreditShoppingTask` / `InfrastReceptionTask` 开始和后续完成事件；该链还必须正常完成且没有其它未识别子任务错误。缺少上下文、错误载荷不同、未知节点、父任务失败、任务链失败或回调无法解析时仍阻断。分类不证明购买成功、线索交流已开启或全部基建待办已完成，也不放宽战斗、奖励识别的错误门禁。

`infrast_check.py inspect --report <原前段报告>` 在校验原日志字节区间及哈希后复用同一分类。对于旧 runner 的 `75`，只有子进程实际为零、没有 runner 异常，且原回调错误全部被上下文消歧时，才返回 `legacy_exit_reclassified=true`；保留 `original_wrapper_exit_code`，不修改旧报告。已消歧项仍作为告警输出，不算“全程无错误”。不能仅凭旧报告中的计数放行，也不能在日志丢失、轮换或哈希不符时重跑前段来掩盖缺口。续跑仍需当前授权、账号和游戏日起点核验；只有 inspect 退出零、无阻断项且业务目标允许继续时，才补剩余阶段。

## 等待长命令

安装、资源更新和完整日常可能数分钟没有输出：

- 普通非交互命令保持 pending，直到退出、超时、取消或运行时失联。
- 宿主返回进程句柄时，采用与任务长度相称的稀疏观察；不要每秒发起 Agent/LLM 轮询。
- 能从同一命令获得新输出时继续等待，不并发启动重复任务。
- 到达合理超时后报告进程、缓存或日志证据，再决定继续等待、取消或诊断。

`FightTimes.times_finished = 0` 不是“尚未开战”或“可以安全停止”的终态证据。MaaCore 会在设置倍率、点击开始和进入战斗前后多次报告当前累计次数；当同一 task 已出现 `StartButton2`、`PRTS1/2/3` 或其他在途战斗节点时，即使累计仍为 0，也应保持原 maa-cli 进程 pending，直到结算、明确错误、超时、运行时失联或用户要求停止。不得仅凭暂时的 0 次结果停止后重启补尾任务。

用户明确要求停止时应及时停止 Agent 启动的 maa-cli，但进程退出不代表游戏中的当前战斗被取消。把账号状态标为需要恢复：先等待或确认在途战斗结果，再使用与实际遗留界面匹配的恢复路径回到安全起点，重新读取理智后才能生成补尾或继续下一个账号。恢复成功不能抹去前一次中断、失败或已发生的资源消耗。

## 结果分类

不要只看一行自然语言，也不要只看退出码。综合：

- 进程退出码；
- maa-cli task summary；
- stderr/终端错误；
- `maa dir log` 下与本次运行对应的日志；
- 必要时的游戏侧可观察状态。

使用以下分类：

| 分类 | 证据与表述 |
|---|---|
| 成功 | 命令正常退出，summary 中预期任务完成，且没有相反错误证据 |
| 部分完成 | 一部分任务完成，另一些失败、跳过或未开始；逐项说明 |
| 正常跳过 | 条件不匹配、资源已满足或当前无可领取内容；不要当成失败 |
| 配置错误 | task/profile 找不到、解析失败、参数在运行时被拒绝 |
| 连接错误 | ADB、端口、设备状态、截图或触控建立失败 |
| 任务错误 | 已连接设备，但识别、导航或具体 MaaCore task 失败 |
| 运行时失联 | 宿主无法继续观察原进程，结果未知；不要宣称失败或成功 |

多账号结果必须逐账号分类；任一账号失败不能把其他账号的结果覆盖，也不能把尚未开始的账号写成失败或成功。

退出码、summary 和日志矛盾时采用保守结论，明确指出冲突。不要为了把结果变成“成功”而连续换端口、重跑整个日常或发出猜测性补偿操作。

maa-cli 自身的热更新可能先于 MaaCore 连接。若 CLI 只输出 `Updating hot update files...` 后以网络 EOF 等错误退出，本次 MaaCore 日志没有新增、账号切换事件也不存在，应分类为“CLI 更新网络失败，业务任务未开始”，而不是切号、ADB 或游戏网络失败。保持窗口、ADB 与进程隔离门后允许一次有界重试；同一前置网络错误再次出现时停止并调查更新源，不把重试成功改写成首次没有失败。

### 收尾检查依赖预检

完整日常在首个账号的业务执行前，把收尾检查依赖纳入执行前业务对账；这属于运行流程，不只适用于首次创建 task。更新 Skill 只更新分发文件，不代表其 MAA 用户资源、检查 task 和 profile 已接入。

- 对已验证奖励布局，按[组件预检](daily-checks.md#开跑前的部署预检)调用只读 `reward_check.py preflight`，核对当前 maa-cli 所使用配置根的扫描 task 和用户资源；另行读取本轮 profile，确认用户资源启用。计划使用理智预检查时，同样核对其捆绑 task、资源与关卡准备页入口。
- 缺少部署时，在当前授权覆盖配置修改的前提下用 `daily_checks.py prepare` 部署；授权未覆盖时先说明变更并询问。冲突文件不自动覆盖。部署后复查，并用本轮 profile dry-run 检查扫描 task 的解析。不能把安装检查或 dry-run 当成游戏页面识别通过。
- 开跑前明确最终 Award 后到达任务页的已验证路径，以及每个账号检查后再切号的顺序。当前页面无需在预检时就在任务页，不为预检启动扫描。
- 无法满足依赖时，先告知无法核验的项目并暂停完整日常；只有用户明确接受本次降级后才继续，最终仍报告未知并提醒。不能静默省略，或到结束才把必需检查改成“下次可选”。执行中的新识别失败继续按收尾未知规则处理，不自动补刷。

### 每账号收尾清单

这是一次日常运行的统一收尾入口。每个账号在业务执行结束后、切号或关闭游戏前按以下顺序对账；已经取得的同账号、本轮有效证据直接复用，不为检查重跑业务任务。临时任务只核验用户要求的范围，不把“只清体力”扩大成完整日常。

1. **理智与资源目标。** 对照本次目标核对终态理智、实际结算次数及资源动作。清体力要求余额不足目标关卡单场消耗，且授权恢复预算已按要求处理；使用[清体力组件](daily-checks.md#清体力日常)校验读数和计算，不用 Fight Completed 代替目标。非清体力任务按自身次数或材料目标判断。
2. **基建结果。** 请求包含基建时，调用[基建日志检查组件](daily-checks.md#基建日志检查)读取薄 runner 报告，分别核对收取、轮换/整理和配置覆盖的逐设施处理，按[独立后置条件](#基建收取与轮换的独立后置条件)判定。脚本未能确认的部分，必要时用已验证的 MAA 路径复核游戏侧状态；不临时重写解析器，也不把无收取日志解释成没有产物。未请求的项目不追加执行。
3. **最终领奖与关键奖励。** 确认最后一次战斗或获授权补尾后已完成最终 Award；已完成则不重复领取。满足[组件起点与部署条件](daily-checks.md#奖励档位一次调用完成扫描与判定)后调用 `reward_check.py scan`，按[每日关键奖励标准](#每日关键奖励收尾检查)确认合成玉和剿灭扫荡券。这是独立检查，不由 Agent 手工数日志。
4. **记录与提醒。** 连同公招、商店等执行前已列出的需求逐项回填完成、正常跳过、未完成或未知及其证据；任一关键奖励不是 claimed 必须明确提醒用户，其他未完成或未知项同样不能隐去。记录该账号结果后才按原有失败隔离规则决定是否切下一个账号；本清单不放宽失败停止条件，也不授权自动补刷、用药或重跑。流程中断或检查起点无法安全恢复时保留未知并报告，不强行继续。

全部账号处理结束后，再执行下面的整体闭环对账。单个账号检查成功不能替代其他账号，也不能证明未来正式入口已经包含本轮临时补偿。

### 汇报前的闭环对账

最后一次修改、恢复或临时补尾完成后，重新读取正式持久化 task，再回到执行前业务对账逐项更新状态。汇报必须把两个问题分开回答：

1. 本次真实运行实际完成了什么；
2. 用户以后调用哪个正式入口时，能够稳定重复哪些行为。

每项肯定结论都要能落到至少一种来源：最终持久化 task 中的明确配置、本次已经说明的跨进程编排，或同一运行边界内的业务后置条件证据。只有临时 task、人工补偿或一次性 Agent 操作完成时，可以确认本次结果，但不能把能力归到另一个正式 task，也不能据此宣称未来入口已经闭环。

最终报告至少说明：

- 正式入口的准确 task 名称；如果没有单一入口，则给出需要依次执行的进程顺序；
- 哪些要求是 `configured`、`orchestrated`、`manual`、`unsupported`、`unverified` 或 `missing`；
- 本次创建的临时 task 承载了什么，以及它是否属于未来正式入口；
- 当前日期未命中的条件分支、尚未确认的账号前置条件和缺少真实 smoke 的能力；
- 本次运行成功但尚未持久化的部分，或已经持久化但本次没有验证的部分。

只要用户要求中仍有 `missing`，或最终持久化入口不能复现刚才依赖临时 task 才完成的关键步骤，就不得用“正式日常已定稿”“以后直接跑这个就行”或“全部完成”概括结果。

### `Completed` 不等于业务后置条件成立

MaaCore 的 `Completed` 或 maa-cli summary 中的完成状态，首先表示对应任务链正常结束。它不自动证明用户描述的领域目标已经全部满足，例如：

- 商店中所有目标商品都已购买；
- 所有可领取奖励都已领取；
- 理智恰好降到零；
- Fight 实际开始过至少一场战斗；
- 请求的公招次数都存在可用槽位并已执行。
- `StartUp` 最终停留在用户要求的目标账号；
- 基建界面中未被当前 mode 覆盖的队列轮换、干员调整或其他底部待办都已处理。

对于购买、领取、确认招募或消耗资源等有状态影响的任务，至少核对一项能证明业务后置条件的额外证据：与本次运行对应的 MaaCore 日志、购买/领取次数、明确的最终界面或用户可接受的游戏侧状态。若只能确认任务链结束，应克制地报告“任务链完成，业务结果未完全核验”。

`Award` 日志中的 `ReceiveAward` 点击可以证明本轮执行了领取动作，但不记录该批奖励的具体物品名称，也不能单独证明某件物品的背包增量。可以据此报告“已领取当时可领取的日常/周常奖励”；只有同时存在物品级日志、库存变化或其他等强度证据时，才确认某张券、某种货币或某件材料已经入账。

### 每日关键奖励收尾检查

每个账号完成最后一次战斗和 Award 后，核对该账号、该服务器游戏日的每日合成玉与剿灭扫荡券是否已经领取。检查发生在切换下一个账号、关闭游戏和最终汇报之前；未完成的账号仍需报告奖励未知，不能用后一个账号结果补齐。

分别报告 `claimed`（包括本轮开始前已领取）、`not_claimed`（确认未领但不区分原因）或 `unknown`；有额外直接证据时可将未领细分为 `claimable`（可领但未领）或 `not_reached`（未达成）。只有直接的物品级领取状态、已验证的档位映射与稳定计数或同等强度证据才能使用 claimed；可领取按钮消失、背包里有券、泛化 Award 完成或整页出现“已领取”均不足够。跨游戏日时重新观察，不沿用上一个游戏日的状态。

任一项不是 claimed，都必须明确提醒用户：能确认缺失时说明“尚未拿到哪项奖励及原因”；识别失败时说明“无法确认哪项是否领取”。不要把 unknown 写成确定没领，也不能省略提醒或称日常全部完成。检查或补领奖失败保留原失败，不自动重跑日常；补刷、吃药、购买或其他资源动作仍需原授权覆盖。

复用[检查组件](daily-checks.md)的 `reward_check.py scan`，不要临时编写识别或累计逻辑。已验证的国服十档适配器根据稳定档位计数推断两项奖励，输出 claimed / not_claimed / unknown；not_claimed 不区分可领未领和未达成，必须提醒而不能自行补刷。不符合该布局、没有完整扫描或结果未知时，不借助 Completed 强行补齐。`Award.orundum` 控制活动幸运墙，不是每日合成玉开关；日常/周常领取由 `Award.award` 控制。

### Depot 库存结果的有效性

按库存计算材料缺口前，核对目标账号本次扫描的任务终态、错误事件与 `DepotInfo` 物品数量。`done = true` 或 `AllTasksCompleted` 不能单独证明扫描成功；空对象、缺少目标物品条目也不能直接解释为零库存。只有成功扫描的覆盖范围与输出语义足以证明目标数量时，才据此计算缺口。

2026-09-05 的一次失败运行同时返回 `DepotInfo` 的 `data = "{}"`、`done = true`，并出现 `TaskChainError`，进程退出码为 1。这种结果应保留为“库存未知”，不能用于推算缺口或自动生成补刷次数；它也不能证明账号确实没有材料。恢复识别或取得用户提供的数量后，再继续依赖库存的计划。

识别失败后的版本与上游修复核查见[安装与环境发现](install-and-discovery.md#识别失败后的版本与修复核查)。

### 基建收取与轮换的独立后置条件

同一个 `Infrast` task 可能依次处理多类目标，汇报时至少拆开判断：

1. 制造站产物、贸易站订单和干员信赖的总览收取；
2. 队列轮换或整理；
3. 当前 `facility` 与 `mode` 明确覆盖的逐设施处理。

一次运行中的轮换、整理或逐设施点击，不能证明总览收取已经发生；反过来，成功收取也不能证明轮换徽标归零或干员已经完成调整。对每个账号都只使用该账号本轮日志边界内的证据，不用另一个账号的成功路径补齐。

总览收取的正向日志证据应包含实际 `InfrastReward` 动作，并能关联到已加载界面中识别出的可收获、订单交付或干员信赖目标。以下路径只能说明任务链正常退出，不能证明“没有可收取内容”：

```text
InfrastNotification -> （没有 InfrastReward） -> InfrastExitReward
```

若通知入口后的 OCR 为空、乱码或只识别到过渡态，随后直接进入 `InfrastExitReward`，将收取分类为 `unverified` 或“疑似因加载/识别时序而跳过”；如果运行后的游戏侧状态仍显示可收获、可交付或可领取信赖的数量，则这是收取未完成的直接反证，应报告失败或未完成。只有可靠证据表明收取面板已经稳定加载且确实没有目标，或存在等强度的游戏侧空状态后置条件，才可以报告“当时没有可收取内容”。`TaskChainCompleted`、进程零退出码和后续轮换动作都不能替代该判断。

上游曾记录同类问题：[Issue #17208](https://github.com/MaaAssistantArknights/MaaAssistantArknights/issues/17208) 描述基建换班有概率不收产物便结束，[PR #17232](https://github.com/MaaAssistantArknights/MaaAssistantArknights/pull/17232) 将根因归为加载遮挡 OCR 后落入退出分支，并增加加载态等待。MaaCore 6.16.8 的资源已包含该分支，但 2026-08-31 的一次真实运行仍出现空 OCR 后直接退出且游戏侧保留待收数量；因此结果核验不能仅依赖版本号或 `Completed`。这项实测只支持保留上述汇报门禁，不代表所有当前版本或每次运行都会复现。

队列轮换/整理则单独核对相应动作与目标后置条件。出现一次 `InfrastRotationClick` 或 `InfrastTrimClick` 只能证明执行过点击；如果用户目标是清空底部待办或完成全部换班，还需核对徽标归零、实际人员变化或同等强度的最终状态。

### 剿灭导航与结算证据

全权委托与普通代理是两条不同的证据链。游戏使用无助战历史最高歼灭数决定全权委托资格和跳过结算；因此按 400 杀完成一次或多次全权委托，只能确认历史最高记录和对应结算成立，不能证明当前保存的普通代理记录完整或本次回放稳定。MAA 在运行中不会持续检查扫荡券数量，券不足后可能回退普通代理；若 task 允许这种回退，普通代理前置状态必须单独验证，不能把全权委托 smoke 外推为连续清理已经可靠。

剿灭导航中命中 `Annihilation@UnableToAgent2`，可以确认 MAA 到达的当前关卡没有呈现可用或已激活的代理状态，并因此无法继续；它不能单独区分该关卡尚未完成 400 杀、代理记录无效或其它游戏侧状态。不要仅凭这个模板断言“剿灭券用完”“周上限已满”或某个唯一根因；同时核对本轮 `stage`、显式选图节点、普通/全权代理节点和周进度证据。

周上限以同一运行边界内 `StageDrops.details.annihilation_weekly_process = [current, limit]` 和 `Annihilation weekly limit reached, stop task` 为直接证据。最后一次结算可能只补足剩余合成玉，并通过 `AP_GAMEPLAY` 返还部分理智；计算最终理智时保留这项返还，再结合 `SanityBeforeStage` 与 `FightTimes.times_finished` 核对实际结算次数。

`UsePrts-Annihilation` 的点击次数也不是剿灭券消耗张数：全权委托可能在进入时已经激活，MaaCore 日志不会记录券库存变化。没有库存前后值或同等强度证据时，可以报告“走过全权/代理路径并完成 N 次结算”，不能精确确认消耗了 N 张券。2026-08-29 的双账号 smoke 中，两个账号均有 6 次剿灭结算和 `1800/1800` 周进度，但只有其中一个账号记录了本轮点击全权委托按钮，验证了这一区分。

普通代理开始后，重复出现 `Fight@PRTS1` 或 `BattleOfficiallyBegin` 只说明 MaaCore 仍能匹配战斗中标志，不等于击杀数或代理流程仍在推进。若同一运行长时间只重复该识别，没有新的阶段、结算、掉落或 `FightTimes` 进展，并且游戏侧出现代理结束、代理异常或等待接管等状态，应判为在途战斗停滞，而不是继续把它当成长时间剿灭等待。不要假设点击接管后 MAA 能继续自动完成；按用户授权停止 maa-cli 后，将账号标为需要恢复，确认实际战斗和理智状态，再决定人工处理、改用有可靠普通代理的关卡或限制为扫荡券覆盖的运行。

多账号时，`StartUp Completed` 与进程退出码零只是门禁的一部分：本次日志若包含登录过期、重新认证或回退到最近账号，就必须覆盖表面成功并判为切号失败。公招时同时核对 `select`/`confirm`：识别到高星组合但未点击确认可能是配置保护而非识别失败。基建时同时核对所选 `mode`：空 `facility` 的总览收取与 `mode = 20000` 的一次游戏内轮换/整理链不是同一行为，后者也不证明左下角待办已经清空。

资源日志也要核对动作字段，而不是只看任务名。2026-08-18 的真实 Fight smoke 中，日志出现 `UseMedicine` 任务/模板但 `details.action = "DoNothing"`，实际没有使用理智药；因此“匹配过资源节点”不能写成“已消耗资源”。只有动作、资源数量变化或其他同等强度证据才能证明实际消耗。

资源结果与战斗结果要独立分类。达到终态的 `FightTimes.times_finished = 0` 仍可能伴随实际临期药消耗；这时可以确认相应资源动作成立，但不能称为已经刷图。核对 `UseMedicine` 的动作、`is_expiring`、`inventory`/`use` 明细和最终理智，再判断目标临期药是否已经用完；仅有 task 配置或一次恢复动作不够。`medicine = 0` 关闭的是普通理智药预算，不会取消非零 `medicine_expire_days` 所授权的临期药策略。后续补尾必须以终态理智计算，并把所有恢复预算归零，避免重复消耗。

固定连战倍率还可能让 Fight 零战斗结束。2026-08-19 实测中，`series = 6` 把 CE-6 的整批消耗算成 216，而当前理智为 205；`FightTimes.times_finished = 0` 后任务仍汇总为 `Completed`。报告“刷图完成”前至少核对实际完成次数或掉落证据；零次应写成正常跳过/部分完成，并说明倍率、当前理智和整批消耗。

反过来，进程尚未结束时出现 `times_finished = 0` 也不能证明这轮最终为零战斗。只有该 Fight 已到达终态，并且没有 `PRTS`、结算、掉落或理智下降等相反证据时，才能把它归类为零战斗正常停止。2026-08-22 的真实 TO-5 运行中，Agent 在累计仍为 0 时停止 maa-cli，但日志随后证明 `PRTS1` 已开始，游戏内单场继续完成并消耗了理智；该事件要求把“终态 + 在途节点”作为停止和补尾计算的联合门禁。

Custom 流程内部的资源错误也可能不升级为 task chain error。例如 namespaced 模板缺失时，日志可记录 `templ not found`，后续分支仍继续并汇总 `Completed`。检查严格购买任务时同时搜索 MaaCore 的 `ERR`、购买按钮/结果节点和最终扫描，不把 summary 覆盖内部错误。

其他内部 `ERR` 也要按证据分层。2026-08-21 的双账号 AP-5 运行中，MaaCore 多次记录 `Unknown task: FightSeries-OldMethodFlag`，但两个账号都存在 AP-5 六连掉落、`FightTimes.times_finished = 6` 和理智 205→25 的一致后置条件，且没有 `TaskChainError`/`SubTaskError`。因此不能仅凭一条内部 ERR 把已证明的战斗结果改写为失败，也不能因业务成功就宣称运行无错误。保留告警、报告已经成立的业务结果，并把具体根因保持为待诊断；缺少后置条件或出现 task chain 错误时仍按失败或结果未知处理。

局部任务失败后再运行恢复任务时，保留原失败证据。后续恢复成功不能把前序运行改写成从未失败；按实际影响报告“部分完成并恢复”或“结果仍不确定”。

### Custom 任务的最小真实验证矩阵

dry-run 不执行 MaaCore 识别链，也不会发现所有模板、命名空间、分支或后置条件问题。资源变更型 Custom 任务在公开复用前，按其实际风险覆盖相关状态：

- 首次运行与重复运行；
- 零个、一个和多个目标；
- 已处理目标位于未处理目标之前；
- 成功后的结果弹窗与局部恢复；
- 余额不足、无可领取内容或其他正常停止状态；
- 从流程可能遗留的中间界面开始。

不要求每个普通用户都重跑完整矩阵，但 Agent 不应把只覆盖一个 happy path 的配置描述为通用可靠方案。

## 文件清理

- 只删除本次创建且已确认路径的候选文件。
- 不自动删除用户备份；交由用户决定，或在当前请求明确包含清理时处理。
- 替换失败时保留原文件与候选并报告，不执行宽泛目录清理。
- 公开报告和仓库不得包含真实设备地址、账号、完整日志或个人绝对路径。
